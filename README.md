# CheckStock — тестовое задание Raketa

Небольшой веб-прототип складского учёта на **Python, FastAPI и PostgreSQL**. Интерфейс адаптирован для ноутбука и телефона. В демо автоматически создаются тестовые товары и два ФФ из задания.

## Возможности

- Матрица физических остатков, резерва FBS и доступного количества по SKU и складам.
- Приход товара на выбранный ФФ.
- Перемещение: при отправке количество списывается с источника и появляется в разделе «Товар в пути»; приёмка увеличивает остаток склада-получателя.
- FBS: резерв уменьшает доступное количество, но не физический остаток; отправка списывает и физический остаток, и резерв; отмена резерва возвращает доступность. После доставки сотрудник может подтвердить её вручную, отправление получает статус DELIVERED.
- FBO: отправка списывает товар с ФФ и создаёт отправку в пути; приёмка маркетплейсом закрывает отправку.
- Нехватка на выбранном ФФ: можно включить распределение по другим активным ФФ. Система проверяет общий доступный остаток и создаёт отдельную FBO-отправку на каждый склад-источник.
- Архивация склада вместо физического удаления: склад исключается из новых операций, но его остатки, движения и ссылки в истории остаются.
- История движений и защита от повторной обработки запроса по `idempotency_key`.

## Быстрый запуск (Docker + PostgreSQL)

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

Откройте <http://localhost:8000>. PostgreSQL будет доступен на порту `5432`. При первом запуске приложение создаёт таблицы и демо-данные:

| SKU | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Остановка:

```bash
docker compose down
```

Чтобы удалить и демо-базу, включая volume:

```bash
docker compose down -v
```

## Запуск без Docker (SQLite для локальной демонстрации)

Для удобства проверки можно запустить прототип на SQLite. В рабочем Docker-сценарии используется PostgreSQL.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Откройте <http://127.0.0.1:8000>. SQLite-файл `checkstock.db` создаётся автоматически.

## Проверки

```bash
pytest -q
```

Проверки покрывают приход и повторный запрос, перемещение и приёмку, резерв/отмену FBS, FBO с распределением по нескольким ФФ и архивацию склада с сохранением остатка.

## Основные API-маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/overview` | Товары, склады, остатки и отправки в пути |
| GET | `/api/history` | История движений |
| POST | `/api/inbound` | Приход товара |
| POST | `/api/transfers` | Создание перемещения |
| POST | `/api/shipments/receive` | Приёмка перемещения или FBO |
| POST | `/api/fbs/reserve` | Резерв FBS |
| POST | `/api/fbs/ship` | Отправка зарезервированного FBS клиенту |
| POST | `/api/fbs/cancel` | Отмена резерва FBS |
| POST | `/api/fbs/deliver` | Подтверждение доставки FBS клиенту |
| POST | `/api/fbo/dispatch` | Отправка FBO, опционально с распределением по ФФ |
| POST | `/api/warehouses` | Создание склада |
| DELETE | `/api/warehouses/{id}` | Архивация склада без удаления истории |

Интерактивная документация API: <http://localhost:8000/docs>.

## Ключевые решения и инварианты учёта

1. `physical` — физически находящееся на ФФ количество. `reserved_fbs` — часть физического остатка, временно заблокированная под FBS. `available = physical - reserved_fbs`.
2. Резерв FBS не уменьшает `physical`; он увеличивает `reserved_fbs`. Поэтому товар нельзя одновременно зарезервировать дважды или отправить через FBO, если он уже зарезервирован.
3. При отправке FBS уменьшаются и `physical`, и `reserved_fbs`. При отмене резерва уменьшается только `reserved_fbs`.
4. При отправке перемещения товар списывается с исходного ФФ и учитывается в `shipments` со статусом `IN_TRANSIT`. На складе-получателе он появляется только после подтверждения приёмки.
5. FBO списывает физический остаток при отправке с ФФ. До приёмки маркетплейсом количество видно как FBO в пути и не возвращается в остатки ФФ.
6. Все изменения остатков и запись движения выполняются в одной транзакции БД. Для PostgreSQL строки остатков блокируются через `SELECT FOR UPDATE` при изменении.
7. `idempotency_key` уникален. Повтор запроса с тем же ключом возвращает результат уже выполненной операции и не повторяет изменение остатка. Повторная приёмка с новым ключом тоже отклоняется по статусу отправки.
8. Склад архивируется (`is_active=false`), а не удаляется физически. Это сохраняет привязку остатков и исторических операций.

## Допущения и границы прототипа

- После отправки FBS заказ отображается в пути к клиенту. Доставка подтверждается вручную сотрудником через интерфейс; после подтверждения отправление получает статус DELIVERED и исчезает из списка отправлений в пути. Интеграция с курьерскими и почтовыми API не реализована. В реальной системе статус можно получать автоматически через API или webhook службы доставки либо подтверждать вручную, если интеграции нет. Возвраты не входят в прототип.
- FBO-приёмка означает подтверждение маркетплейсом; складской остаток ФФ повторно не увеличивается.
- Распределение FBO при нехватке на выбранном ФФ — автоматическое списание с доступных активных ФФ в рамках одной транзакции, с отдельной записью отправки для каждого источника.
- Авторизация, роли пользователей, интеграции с реальными API маркетплейсов, миграции Alembic и промышленный мониторинг не входят в объём однодневного прототипа.
- В production следует дополнить конкурентные операции полноценным уровнем блокировок/повтором транзакций и вынести миграции схемы в Alembic. Текущий прототип уже использует транзакции и row-level locking на PostgreSQL для изменяемых остатков.
